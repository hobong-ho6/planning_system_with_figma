# 엑셀 다국어 번역 검증 로직 정리

> 7개 파일(Unifi WEB BROWSER 2종, sampleformat 3종, xlt_output 1종) 검증 경험을 종합한 표준 프로세스입니다.

> ⛔ **이 문서는 CLAUDE.md '⛔ 번역 품질 게이트'의 실행 절차다.** 게이트 요건 자체(자동 P0=0은 시작점 · 전체 행 전수 수동 검토 · en_US 원문 검토 · 수동 3단계 체크표+건별 처리 판정 · `check_gate_report.py` exit 0)는 **CLAUDE.md가 정본**이므로 여기 반복하지 않는다 — 이 문서는 그 요건을 **어떻게 수행하는지**(패턴 사전·체크표·판정 기준)를 담당한다.
> **오탐 주의 — 조사·받침 판정은 정확히**: `바임`은 종성 `ㅁ`(받침 있음)이므로 `(바임)으로부터`가 **정상**(받침 없는 명사만 `로부터`). 받침 유무는 마지막 음절의 종성으로 판정한다.

## 📌 핵심 원칙

검증은 항상 **3단계 순서**로 진행하고, 한국어 원문을 먼저 정리해야 다국어 일관성이 보장됩니다.

```
[사전 준비]
   파일 구조 파악 (시트, 행 수, key 열, 언어 채움 비율)
        ↓
[1단계] 한국어 맞춤법·띄어쓰기 (원문 정리)
        ↓
[2단계] 용어집 위반 (표준 표기 점검)
        ↓
[3단계] 다른 언어 번역 검토 (자연스러움 확인)
        ↓
[작업 1] 발견 사항 우선순위 분류 (P0/P1/P2)
[작업 2] 엑셀 파일 업데이트 (셀 단위 정밀 변경)
[작업 3] 신규 번역 추가 (해당 시)
```

## 🔧 사전 준비

### 필요 파일

| 파일 | 용도 |
|---|---|
| `*.xlsx` | 검증 대상 |
| `glossary.json` | 용어집 캐시 — 버전·용어 수는 API 조회 시점 기준 (`fetch_glossary.py`로 매번 갱신) |
| `validate_translation.py` | 자동 검증 스크립트 |

### 파일 구조 파악 (검증 시작 전 필수)

```python
import pandas as pd
df = pd.read_excel(path, sheet_name='properties')
print(f"행 수: {len(df)}")
print(f"컬럼: {df.columns.tolist()}")
for col in df.columns:
    filled = df[col].notna().sum()
    print(f"  {col}: {filled}/{len(df)} ({filled/len(df)*100:.1f}%)")
```

다음 항목을 확인:

| 확인 항목 | 의미 |
|---|---|
| **시트 이름** | 보통 `properties`, 일부 `plurals` 등 추가 시트 존재 |
| **key 열 이름** | `Key ID` 명시적 또는 첫 번째 열(`Unnamed: 0`) |
| **전체 행 수** | 검증 범위 파악 (6~1583행까지 다양) |
| **언어 열 구성** | 5개 채움(en/ko/ja/zh_TW/th)이 표준, 일부 파일은 19개 전체 컬럼 |
| **각 언어 채움 비율** | 100% 채움 vs 미사용 언어 vs 한국어만 채움 (신규 번역 대상) |

### 자동 검증 스크립트 실행

```bash
python validate_translation.py {파일.xlsx} \
  --sheet properties \
  --key-column "Key ID" \
  --glossary glossary.json \
  --output report.md \
  --json result.json
```

자동 검증이 잡는 항목:
- 빈칸, 언어 문자 혼입, placeholder/줄바꿈 불일치
- `/n` 오타, 용어집 예외 패턴 표기 (USDT/JPYC/PIN/API 등)
- 한국어→다른 언어 용어집 매칭

**중요**: 자동 검증은 시작점일 뿐, 진짜 품질은 수동 검토에서 결정됩니다.

### 2차 독립 검토 (`translation-reviewer` 에이전트 — 2026-07-30 신설, 권장)

수동 3단계를 **1차 번역자가 자기 결과를 검토**하면 확증 편향이 생긴다. 아래 상황에서는 `.claude/agents/translation-reviewer.md` 에이전트를 호출해 **분리된 컨텍스트로 재판정**받는다.

- 신규·변경 키가 **5키 이상**이거나, 유의사항·약관처럼 **긴 문장 키**가 포함될 때
- 용어집 등재를 제안하기 전 (중복 등재·일관성 오판 방지)
- 사용자가 "검증/verify"로 **전수 점검**을 요청했을 때

호출 방식·기대 산출물:
- 입력: `translation_data.json`(또는 대상 엑셀) + **호출자가 라이브 조회해 저장한** `scripts/glossary.json` + 범위 지시. 에이전트는 용어집 API를 다시 부르지 않는다.
- 출력: `🔴 실제 결함 / 🟡 확인 필요 / ⚪ 1차 판정 동의` 3분류 표 + "1차가 놓친 것" + 전수 점검 확인. **에이전트는 번역·파일을 수정하지 않는다**(읽기 전용).
- 반환된 🔴은 게이트 리포트 (b)·(c)에 반영하고, 🟡은 사용자 확인 사항으로 올린다.
- 실측 근거: 1차가 `선물하기`의 기존 용어집 등재(v3.6)를 놓치고 중복 등재를 제안한 사례(2026-07-30) — 독립 컨텍스트가 `grep` 한 번으로 잡는 유형이다.

### Figma 원문 수정 요청 취합 (`figma-source-issues` 에이전트 — 2026-07-30 신설)

게이트 리포트의 **`(1a)` 원문 교정 표**와 **`(d-2)` 원문 개선 제안**은 리포트마다 흩어져 쌓인다(현재 45건+). 번역은 교정본을 반영해도 **Figma 원본은 그대로**라 다음 추출에서 같은 오타가 다시 들어온다.

- **호출 시점**: ⓐ 사용자가 "디자이너에게 정리 요청할 목록"을 원할 때 ⓑ 세션 정리·핸드오프 때 미처리 원문 오타를 확인할 때 ⓒ 같은 프레임을 다시 작업하기 전(중복 지적 방지)
- 에이전트는 전 리포트를 스캔해 **중복 제거·유형 분류(오타/띄어쓰기/nbsp/표기 불일치/모호)·우선순위**로 묶고, nbsp·말미 공백을 `[nbsp]`·`␣`로 **보이게 표기**한다(디자이너가 눈으로 못 보는 문자가 핵심 가치).
- `FIGMA_TOKEN`을 주면 **현재 원문에 아직 남아 있는지**(`잔존`/`수정됨`/`확인불가`)까지 대조한다.
- 번역 쪽 판단(정상 의역·마침표 정책·용어집 오탐)과 **사용자가 원문 유지로 확정한 항목은 제외**한다 — 디자이너 할 일이 아니다.

## 📝 1단계: 한국어 맞춤법·띄어쓰기

> 💡 국문 교정 보조 도구(공식 룰 권장): https://nara-speller.co.kr/speller/

### A. 자동 검출 가능 항목 (스크립트로 처리)

| 카테고리 | 검사 패턴 | 예시 |
|---|---|---|
| 🔴 오타 | `미선` (특정 단어) | `미선하고` → `미션하고` |
| 🔴 맞춤법 | `되요\b` | `지급되요` → `지급돼요` |
| 🔴 맞춤법 | `됬` | `소진됬` → `소진됐` |
| 🔴 띄어쓰기 | `(유지\|사용\|발생\|종료\|시작)시(?=\s\|$\|에\|는\|를)` | `유지시` → `유지 시` |
| 🔴 띄어쓰기 | `할수있\|할수없\|볼수있` | `할수있` → `할 수 있` |
| 🔴 비표준 공백 | `\xa0` (non-breaking space) | 끝에 잔존 공백 |
| 🟡 공백 | `\s{2,}` 이중 공백, 앞뒤 공백 | |
| 🔴 `/n` 오타 | 슬래시 + n (백슬래시 누락) | `여기서/n부터` → `여기서\n부터` |

### B. 수동 검토 필요 항목 (사람이 직접 봐야 함)

자동 도구로는 잡을 수 없으니 한국어 셀을 하나씩 읽으며 검토:

#### B-1. 표현 어색 (가장 흔한 케이스)

| 패턴 | 빈도 | 권장 수정 |
|---|---|---|
| `미션하고` | ⭐⭐⭐ 매우 자주 | `미션 완료하고` |
| `미션 참여하고` | ⭐⭐ 자주 | `미션을 완료하고` |
| `정보가변경된` | ⭐ 가끔 | `정보가 변경된` (조사 뒤 띄어쓰기) |
| `누리고다양한` | ⭐ 가끔 | `누리고 다양한` (어미 뒤 띄어쓰기) |

#### B-2. 외국어 음역의 어색함

| 패턴 | 발견 사례 | 권장 수정 |
|---|---|---|
| 일본어 음역 잔존 | `포이가츠` (일 `ポイ活` 음역) | `포인트` (EN: point) |
| 일본어 직역 | `친구추가` | 컨텍스트에 따라 |

→ 검사 방법: EN/JA/ZH/TH의 표현이 한국어와 의미상 일치하는지 비교.

#### B-3. 의미 모호한 단어

| 패턴 | 발견 사례 | 권장 수정 |
|---|---|---|
| 직역으로 의미 약화 | `실물 결제` (EN: in-store payments) | `매장 결제` |
| 다의어 충돌 | `피부결과 윤곽` (피부 결+과 vs 피부 결과+윤곽) | `피부결, 윤곽` |

#### B-4. 동일 표현 중복

```
"자세한 자산 정보는 표시되지 않을 수 있으며 자세한 자산 정보는 여기서 확인해 주세요."
```
→ 같은 어구가 한 문장 내 두 번 등장. 두 문장으로 분리하거나 두 번째 생략.

#### B-5. 조사 오류

| 패턴 | 규칙 |
|---|---|
| `(바임)으로부터` | 받침 없는 명사는 "로부터" (✓ `(바임)로부터`) |
| `JPYC가 {1} 지급` | placeholder 뒤 조사 누락 (✓ `{1}에 지급`) |

#### B-6. 띄어쓰기 일관성

같은 파일 내 동일 단어가 다르게 띄어 쓰임:
- `필수 미션` vs `필수미션` 혼용 → 통일
- `출석체크` (합성어 굳어짐) vs `출석 체크` (표준) → 정책 결정

#### B-7. 종결 어미 / 마침표 일관성

| 어미 | 마침표 사용 |
|---|---|
| `-습니다`, `-주세요` (합쇼체) | ○ (안내 메시지) |
| `-어요`, `-아요` (해요체) | ✕ (캐주얼 UI) |
| 명사형 (`받기`, `둘러보기`) | ✕ (UI 라벨) |

#### B-7-1. 공식 룰 표기 스타일 (guide.md §5-1 — 2026-07-27 추가)

| 검사 | 예시 | 처리 |
|---|---|---|
| 한글·영어 혼용 | `Gas Fee 확인` | 완전한 한국어 표현으로 |
| 줄임말 | `Tx` | `Transaction` 전체 표기 |
| 금지/지양 용어 | `앱스`·`월렛`·`Yield/APY`·`원금 보장` 등 | guide.md §5-1 C·D 표 기준 대체 |
| JP 띄어쓰기 | `年利 5.5% 適用中` (숫자+단위 띄움) | 붙임 (`年利5.5%適用中`) |
| TH 띄어쓰기 | `5.5%ต่อปี` (단위 붙음) | 의미 단위 분리 (`5.5% ต่อปี`) |
| 날짜/시간 표시 | 문장 중간 하드코딩 날짜 (`이벤트 종료일은 2026-08-01 입니다`) | 변수화 제안(`{{date}}`) — 문장 끝·단독 날짜는 키 제외 검토. 포맷: 태국 외 `YYYY-MM-DD`, 태국 `DD-MM-YYYY` (guide.md §5-1 A) |
| URL 링크 태그 | 문장 일부 링크인데 태그 없음 / 전체 링크인데 `<a>` 포함 | 일부 링크 = `<a>텍스트</a>` + URL 기획서 기재, 전체 링크 = 태그 없이 기획서만 (guide.md §5-1 A) |

#### B-8. 구두점 / 쉼표

| 패턴 | 발견 사례 | 권장 |
|---|---|---|
| 대구 구조 | `엔화 가치는 그대로 송금은 더 빠르게` | 쉼표 추가 |
| 마침표 vs 쉼표 | `덕질의 성지. BTS가 머물렀던...` (EN은 대시) | 컨텍스트 검토 |

## 📚 2단계: 용어집 위반

### A. 용어집 매칭 (한국어 → 다른 언어)

한국어 셀에 용어집 키워드가 들어 있으면 다른 언어 셀에 지정 번역어가 있는지 확인.
긴 용어 우선 매칭 (예: "거래 내역" > "거래").

**🚨 중요**: 용어집 매칭 위반의 **대부분은 정상 의역**입니다.

#### 정상 의역으로 판정되는 패턴 (수정 불필요)

| KO | 위반 패턴 | 평가 사유 |
|---|---|---|
| 송금 | EN `transfer/transferring` (X `send`) | 금융 도메인 표준 |
| 송금 | TH `โอนเงิน` (X `ส่ง`) | 태국어 금융 표준 |
| 확인 | EN `OK/Confirm/View` (X `check`) | UI 버튼 라벨 |
| 확인 | TH `ตกลง/ดู` (X `ตรวจสอบ`) | UI 버튼 라벨 |
| 변경 | ZH `變更/變動` (X `更換`) | 동의어, 공식 문서 표준 |
| 자산 | EN `funds` (컨텍스트) | "Add funds" 같은 표현 |

→ 리포트에 표시하되 **수정하지 않음**. 용어집 자체 보완이 더 적절.

> 💡 **용어집 업데이트 권장(필수 안내)**: 같은 용어가 ⓐ 정상 의역으로 반복 P1 오탐되거나, ⓑ 용어집에 없는데 도메인에서 자주 쓰이면 — **용어집(API) 보완이 근본 해결**이다. 해당 용어 + **5개 언어 권장 표기**를 정리해 **사용자에게 "용어집 업데이트 권장"으로 안내**한다(엑셀만 고치면 다음 파일에서 또 오탐). 용어집은 임의 수정하지 않는다. → 산출·전달 절차(API 읽기 전용·**전체 JSON 산출 → 사용자가 Landpress CMS 붙여넣기**)는 `md/landpress.md` 참조.

#### 진짜 오류로 판정되는 패턴 (수정 필요)

- 한국어 원문이 다른 언어에 그대로 들어감 ("거래 내역 정렬" → 4개 언어 모두 동일)
- 한국어 한자/한글이 다른 언어에 잔존 (`友だ치` 같은 한국어 "치")
- placeholder만 다른 경우

### B. 예외 패턴 표기 통일

용어집의 8개 예외 패턴은 정확한 표기 필수:

| 패턴 | 모든 언어 |
|---|---|
| USDT, JPYC, IDRP, PIN, API, URL | 정확히 대문자 |
| Apple, Google | 정확히 표기 |

**검사 시 단어 경계 주의**:
- `idrp.io`, `jpyc.co.jp` 같은 **도메인 내 부분 문자열은 제외**
- `api_key`, `apple_pay` 같은 **식별자 내 부분 문자열도 제외**

### C. zh_TW 한자 변형

| 표준 (U+) | 이형 (U+) | 의미 |

header = {ws.cell(row=1, column=c).value: c for c in range(1, ws.max_column + 1)}

## 🚨 자주 발견되는 함정

### 1. 자동 도구가 못 잡는 한국어 어색함

자동 도구가 보지 못하는 표현:
- "미션하고", "미션 참여하고"
- "자세한 자산 정보 중복"
- "피부결과 윤곽" (다의어 충돌)

→ **반드시 사람이 한 줄씩 읽으며 검토**.

### 2. 용어집 위반 ≠ 진짜 오류

자동 검증으로 1000+ 건의 용어집 매칭 위반이 나와도 95%는 정상 의역:
- 송금→transfer (금융 표준)
- 확인→OK (버튼 라벨)

→ **위반 건수에 놀라지 말고 진짜 오류만 골라내기**.

#### 2-1. ⛔ 매칭은 "ko_KR 부분일치" — 구조적 오탐 (재제안 금지)

`validate_translation.py` 2단계는 `if ko_term in ko_text` → 각 언어 셀에 `correct_trans` 부분일치를 요구한다. 여기서 구조적으로 오탐이 난다:

- **(A) en 대소문자·굴절 — ✅ 2026-07-28 해소(검증기 개선).** `TranslationValidator._term_in_text`가 **en_US만 casefold + 규칙 어미(`s·es·d·ed·ing`, `y→ies`, `e→ing`) 허용**으로 비교한다. `Invite`/`Friends`/`Gifted`/`Copies` 같은 정상 표기는 더 이상 P1이 아니다(실측: 럭키볼 73키 P1 124 → 101, 신규 term 유래 오탐 14 → 6). 다른 언어는 대소문자·굴절이 없어 완전일치 비교를 유지한다. **판정을 느슨하게만 바꾼 것이라 기존 검출은 그대로 유지된다.**
  - 남는 en 오탐은 **불규칙 변화·동의어**뿐이다 — `당첨→win` vs `won`, `최대→Max` vs `up to`, `확인→check` vs `OK`/`verified`. 이는 (B)와 같은 성격이니 오탐 판정으로 처리한다.
- **(B) 다의어** — ko 한 단어가 문맥별로 갈리는데 매핑은 1:1이라, 어느 쪽으로 등재해도 반대쪽이 전부 P1이 된다.

**`확인`(대표 사례, 럭키볼 실측 P1 10건 → 검증기 개선 후 **8건**) — 사용자 확정: 현행 유지(조회 의미), 오탐 판정으로 처리.**

| 문맥 | 정확한 번역 | 용어집(조회 의미) |
|---|---|---|
| 버튼 OK (`mini_luckyball_confirm`) | OK / 確認 / 確認 / ตกลง | en·zh·th 3건 P1 |
| 둘러보기 (`missions_promo`) | Check out / ดู | th 1건 P1 (en 대소문자 건은 2026-07-28 개선으로 해소) |
| 조회·검증 (`oa_followed`·`must_check`·`social_link_desc`·`terms_info_change`) | check / verify / 查看 | 5건 P1 |

→ **이 8건은 매 실행 재현되는 확정 오탐이다**(불규칙·동의어 유형이라 검증기 개선으로도 남는다). 게이트 (c)에서 "오탐" 판정만 남기고, **(d-1) 용어집 보완으로 재제안하지 않는다.** 검토 결과 세 방안 모두 부적합했다: ⓐ `확인(버튼)` 별도 키 추가는 ko `확인`에 매칭되지 않아 **무효**, ⓑ 버튼 의미로 교체하면 동사 `확인` 5행이 새로 깨져 **악화**, ⓒ 삭제는 조회 의미 표준 표기가 사라짐 → 사용자가 ⓒ 대신 현행 유지를 선택.

**`홈` — 사용자 확정: 등재 보류.** 사용 1행(`go_home`)뿐이라 `md/landpress.md` §4 기준 1(반복 사용) 미달이고, `홈`→en `Home`으로 등재하면 현행 `Go to home`(소문자 h)이 (A)에 걸려 **없던 P1이 생긴다**(§4 기준 3 위반). 표기 기준은 기존 `홈으로 이동`(en `Go to Home`) 항목으로 충분.

> **일반 규칙**: (d-1) 용어집 보완을 권장하기 전에 **후보를 실제 파일에 적용해 P1 증감을 계산**한다. 오탐이 반복된다는 사실만으로 등재를 권하면 오탐을 늘릴 수 있다.

### 3. 영어 원문 오타가 한국어로 전파

`perksand` → 한국어에도 `누리고다양한`이 그대로 들어감.

→ **영어 원문 파일이면 영어부터 검토**.

### 4. 컬럼 swap은 데이터 입력 단계의 시스템적 오류

`en_US`에 한글 + `ko_KR`에 영어 → 단순 오타가 아닌 데이터 입력 시스템 오류.

→ **CMS/시스템에서 같은 패턴이 재발할 수 있으므로 근본 원인 파악 필요**.

#### 4-1. 단일 언어 패치는 컬럼 정렬 검증 후 (⛔ 재발 방지)

"일본어만 업데이트"처럼 **한 언어만 바꾸는 키 단위 패치**에서, 바꿀 언어 diff만 보고 덮어쓰면 안 된다. 컬럼이 어긋난 키(`ja` 칸에 한국어, `en` 칸에 일본어가 든 회전 어긋남)를 그대로 덮어쓰면 **그 칸에 있던 다른 언어의 유일한 원본이 소실**된다.

- **실측(2026-07)**: Guide Kim LV `mini_guidekim_cat_eye`(`ko`=Ophthalmology·`en`=眼科·`ja`=안과)에 `ja`만 위키 일본어(`眼科`)로 덮어써 **한국어 `안과`가 소실**. 사용자가 "언어 열에 맞춰 업데이트 안 됨"으로 지적.
- **원칙**: 단일/일부 언어 패치 전, 대상 키의 **5개 언어 셀을 전부 위키 다국어 표(정본)와 대조**해 정렬을 확인한다. misalignment가 있으면 단일 언어 패치 금지 — 어긋난 컬럼 전부를 정본으로 realign한다. 위키 표가 정렬 정본. (`md/translate.md` 키 단위 번역 패치 모드 Step 2-1)
- **코드 강제(2026-07-09)**: `scripts/patch_translation.py`의 `apply_translation_patch`가 **패치 후에도 대상 행에 이질 문자체계가 남으면 `ValueError`로 차단**한다(공유 검출기 `TranslationValidator.foreign_script_issues`). 단일 언어 패치가 회전 어긋남 행을 그대로 두는 것을 코드가 막으므로, 어긋난 컬럼 전부 realign 후에만 통과한다. 의도적 예외만 `allow_misaligned=True`.

### 5. 마침표 정책은 언어별로 다름

| 언어 | 일반 정책 |
|---|---|
| KO | 해요체 ✕, 합쇼체 ○ (혼용 빈번) |
| TH | 사용 안 함 (관습) |
| EN/JA/ZH | 평서문 ○ |

→ **KO ↔ TH 불일치는 정상**, KO ↔ 다른 언어는 정책 결정.

### 6. 비표준 공백(`\xa0`)은 보이지 않음

복사·붙여넣기 시 자주 혼입되며 매칭 실패 원인:
```python
# 매칭 실패 케이스
actual = 'foo\xa0'   # 끝에 non-breaking space
expected = 'foo'      # 일반 공백
# actual == expected → False
```
→ **수정 작업 전 `\xa0` 사전 정리**.

### 7. 한자 변형은 시각적으로 구분 어려움

`產` (U+7522) vs `産` (U+7523) — 거의 동일해 보이지만 유니코드 다름.

→ **항상 유니코드 비교로 검사** (`ord(c)`).
