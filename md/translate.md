# Figma → 다국어 번역 절차

## 개요
Figma 파일에서 화면별 텍스트 노드를 추출하고, 다국어 번역을 수행하여 XLT Key 기반 번역 데이터를 생성하는 절차.

추출 모드는 세 가지다 — ① `(New)` 프레임 전수, ② 단일 프레임, ③ 코멘트 선별(`XLT` 코멘트가 가리키는 텍스트만, Step 1 "코멘트 선별 모드" 참조). 모드가 무엇이든 Step 2~7(XLT Key·번역·검증·엑셀)은 동일하다.

별도로, **이미 반영된 번역에서 특정 XLT Key의 일부 언어만 고치는** 경우는 Figma 추출 없이 **"키 단위 번역 패치 모드"**(이 문서 하단 절)를 쓴다 — 한국어 변경 시 재번역, 특정 언어 최종본만 교체 등을 키·언어 단위로 처리한다.

`md/guide.md`에서 규정하는 사항:

## 절차

### ⚠️ 프로덕션 환경 주의사항

**이 절차는 실제 서비스에 사용되는 번역 데이터를 생성합니다:**

- ❌ 샘플링 금지: "처음 10개만", "일부만" 절대 금지
- ❌ 데모 모드 금지: "예시로 몇 개만" 절대 금지
- ✅ 전체 처리 필수: 모든 텍스트, 모든 언어 완전 처리
- ✅ 사용자 확인: 처리할 텍스트 개수를 명시하고 진행 확인

**시작 전 사용자에게 확인받을 내용:**
```
이 Figma 파일에서 총 XXX개의 텍스트를 추출했습니다.
5개 언어(ko_KR, ja_JP, en_US, th_TH, zh_TW)로 완전 번역을 진행합니다.
예상 소요 시간: YY분

전체 번역을 진행하시겠습니까? (Y/N)
```

### Step 1: 텍스트 노드 추출

**⚠️ 전체 추출 필수 — 샘플링 금지**

1. `use_figma`로 대상 페이지 설정 (`setCurrentPageAsync`)
2. **추출 대상 프레임 필터링**: 현재 페이지의 직속 자식 프레임 중 이름이 `(New)`로 시작하는 프레임만 추출 대상으로 한다. 단, 이름이 `(x)`로 시작하는 프레임(작업 중단·삭제 예정)은 제외한다
   - 이 필터는 **번역 텍스트 추출에만 적용**된다 — 2단계 프로토타입은 전체 프레임·전체 인터랙션을 수집하고(`(x)` 포함), 3단계 위키는 `Case`/`(x)` 시작 프레임을 제외한다 (CLAUDE.md '단계별 프레임 필터 규칙' 참조)
   - 필터링 결과(대상 프레임 수 / 전체 프레임 수)를 사용자에게 보고한다
   - **단일 프레임 모드**: 사용자가 특정 프레임 URL을 지정하면(예: "이 프레임만 다국어 번역 후 위키 업데이트") `(New)` 필터 대신 **그 프레임 하나만** 추출 대상으로 한다. URL의 node-id로 해당 프레임을 찾아 그 안의 텍스트만 `findAll`로 추출한다. 이름이 `(x)`로 시작하면 경고 후 사용자 의사 우선. XLT Key 정의·5개 언어 번역·검증(Step 2~5)은 그 프레임 텍스트에만 동일하게 적용하고, 산출물(XLT Key + 번역 데이터)은 위키 단일 프레임 모드(`md/wiki.md` Mode B)의 XLT 컬럼·다국어 번역 섹션 입력으로 넘긴다
   - **코멘트 선별 모드**: 사용자가 "Figma 코멘트(`XLT`)로 표시한 문구만 번역"을 요청하면 `(New)`/단일 프레임 필터 대신 **`XLT` 코멘트가 가리키는 텍스트만** 추출 대상으로 한다. 상세 절차는 아래 **"코멘트 선별 모드"** 절 참조
3. 대상 프레임에서 `findAll(n => n.type === 'TEXT')` 실행
   - ⚠️ `findAll`은 반드시 **현재 페이지의 자식 프레임**에서만 실행한다. document 루트에서 실행하면 파일 전체(다른 페이지 포함)가 탐색되어 다른 페이지의 텍스트가 섞여 들어온다
   - `setCurrentPageAsync`를 건너뛴 채 추출하지 않는다
4. 추출 데이터:
   - `characters` (텍스트 내용)
   - `x, y, w, h` (화면 내 상대 좌표)
5. 중복 텍스트 제거 및 고유 텍스트 목록 생성

**실무 팁 (MCP 도구 출력 제한):**
- `use_figma` 결과는 **약 20KB에서 잘린다** — 화면이 많으면 한 번에 전체를 반환하지 말고 **프레임당(또는 2~3개씩) 나눠 호출**한다
- 반복 텍스트(자산 목록 등)는 `{text, count, pos[]}` 형태로 **동일 텍스트를 그룹핑**해 반환하면 출력량이 크게 줄어든다 (89개 노드 → 고유 37개 수준)
- 추출 결과는 `translation_extract.json`으로 저장한다 — 2단계(프로토타입)의 textNodes/i18n 생성 입력으로 재사용되므로 재추출이 불필요해진다

**추출 완료 후 사용자에게 보고:**
```
✓ 총 {total_screens}개 화면에서 {total_texts}개 고유 텍스트 추출 완료
- 화면별 평균: {avg_per_screen}개
- 최소/최대: {min}/{max}개
```

#### 코멘트 선별 모드 (`XLT` 코멘트 기반)

`(New)` 전수 추출·단일 프레임 모드와 **별개의 세 번째 모드**다. 디자이너가 번역 대상 문구 위(또는 근처)에 본문이 `XLT`로 시작하는 Figma 코멘트를 달면, 그 코멘트가 가리키는 텍스트만 골라 번역한다. (기존 두 모드는 그대로 유지.)

**마커 규칙**: 코멘트 본문(`message`)을 trim·소문자화했을 때 **`xlt`로 시작**하면 대상이다 — 대소문자 무시, 뒤따르는 `:`·공백 등은 무관하다. (실측: 실제 파일의 마커는 콜론 없는 `XLT` 단독이 일반적이며 `xlt:` 형태도 허용한다.)

**트리거**: 사용자가 "Figma 코멘트(`XLT`)로 표시한 문구만 번역" 류로 요청 + Figma URL(페이지 또는 프레임) 제공 시.

**대상 선택자는 위키 번호가 아니라 코멘트 본문의 `XLT` 마커다.** 위키 Screen 표 Description의 번호(`1.`, `2.`…)는 미해결 코멘트의 y정렬 순번이라 코멘트 추가/해결 시 밀린다. 이 모드는 **실시간 Figma 코멘트를 다시 읽어 `XLT` 마커로 대상을 선택**한다 — 위키 번호는 사람이 교차 확인하는 라벨로만 쓴다.

**절차:**

1. `setCurrentPageAsync`로 대상 페이지 설정(또는 프레임 URL이면 그 프레임으로 한정).
2. **`XLT` 코멘트 수집 (⚠️ 캐시 금지 — 매 실행마다 새로 조회)** — `md/wiki.md`의 코멘트 조회 절차 중 **REST 직접 조회**(`GET /v1/files/{fileKey}/comments`)만 사용한다. **`comments_data.json` 등 캐시·이전 수집 결과를 재사용하지 않는다** (wiki.md의 "comments_data.json 재사용" 경로를 이 모드에서는 적용하지 않음). XLT 마커·코멘트는 추가·해결·이동·삭제될 수 있어, 캐시를 쓰면 사라졌거나 바뀐 마커를 잘못 선별할 수 있으므로 **매 번역 실행마다 Figma에서 최신 코멘트를 새로 가져온다.** 조회는 반드시 `scripts/fetch_comments.py`의 **`fetch_threads(file_key, token, node_ids=대상 노드집합)`** 로 한다(REST 직접 + `parent_id` 답글 매칭 + `log_self_check` 누락 가시화) — **`fetch_comments_raw`를 직접 호출해 `if parent_id: continue`로 루트만 거르지 말 것**(답글 누락, wiki.md Step 3 안티패턴). 미해결(`resolved_at` null) 루트 중 마커 규칙(위)에 맞는 것을 고르되 **각 스레드의 `replies`까지 읽는다** — 디자이너가 XLT **키명을 루트가 아니라 답글에** `XLT - KEY`/`xlt key = KEY`/`XLT Key = ... KEY` 형식으로 지정할 수 있다(2026-07-03 reward 프레임 실측; 정책 코멘트의 답글에 키가 오기도 함). 각 `{id, node_id, x, y, message, replies}`를 보관하고, 키명 추출은 message+replies에서 마지막 식별자(`UF_\w+|mini_\w+|common_\w+`)를 취한다.
3. 각 `XLT` 코멘트의 **대상 텍스트를 매칭**한다(아래 매칭 알고리즘).
4. 매칭된 텍스트를 중복 제거한다 — **동일 한국어 원문 = 1개 키** 불변 규칙(Step 2) 준수. 원문 줄바꿈(`\n`)은 ko_KR에 보존하고, 매칭 lookup은 `\n`→공백 정규화로 비교한다.
5. **확인 단계**(아래)에서 사용자 승인 후, 승인된 텍스트만으로 `translation_extract.json`을 생성한다(스키마 동일, `items`가 선별분만 포함). 이후 **Step 2~7을 그대로** 수행한다 (Step 5 **번역 품질 게이트** 포함 — XLT만 번역해도 검증 리포트 제시를 생략하지 않는다).

**매칭 알고리즘 (코멘트 → 텍스트):**

좌표는 **절대좌표로 환산**해 비교한다 — 코멘트의 `node_id`가 최상위 프레임이 아닌 중첩 컨테이너일 수 있어 `node_offset`이 화면-상대 좌표와 어긋날 수 있기 때문이다.
- 코멘트 절대점 = `absoluteBoundingBox(node_id).{x,y}` + `node_offset.{x,y}`
- 텍스트 절대 bbox = 각 TEXT 노드의 `absoluteBoundingBox`

1. **`node_id`가 TEXT 노드면** → 그 노드의 `characters`를 바로 사용한다 (정확, `매칭방식=직접`).
2. **아니면(프레임/컨테이너)** → 코멘트 절대점을 **포함하는** 텍스트 중 **가장 작은(가장 구체적인) bbox**를 선택한다 — 텍스트가 겹쳐 여러 개가 포함될 때 큰 박스를 잘못 잡는 것을 막는다(실측 검증됨). 포함이 없으면 중심거리 **최근접**(합리적 반경 내)을 선택한다 (`매칭방식=좌표`).
3. 반경 내 후보가 없으면 → **`매칭 실패`로 표시**하고 자동 선택하지 않는다.

```python
# text_nodes: [{ "t": 원문, "abs": [x, y, w, h] }]  (REST nodes 또는 use_figma findAll + absoluteBoundingBox)
def match(comment_pt, text_nodes, radius=60):   # radius(px)는 화면 밀도에 맞게 조정
    cx, cy = comment_pt
    inside = [n for n in text_nodes
              if n["abs"][0] <= cx <= n["abs"][0] + n["abs"][2]
              and n["abs"][1] <= cy <= n["abs"][1] + n["abs"][3]]
    if inside:
        return min(inside, key=lambda n: n["abs"][2] * n["abs"][3])  # 포함 중 최소(구체적) bbox
    def dist(n):
        nx = n["abs"][0] + n["abs"][2] / 2
        ny = n["abs"][1] + n["abs"][3] / 2
        return ((nx - cx) ** 2 + (ny - cy) ** 2) ** 0.5
    cand = min(text_nodes, key=dist, default=None)
    return cand if cand and dist(cand) <= radius else None   # 없으면 매칭 실패
```

**확인 단계 (필수 — 좌표 휴리스틱 오매칭 차단):**

번역 실행 전 다음 표를 사용자에게 제시하고 승인받는다. 사용자가 오매칭/실패 항목을 제거·교정한 뒤 승인하면 **승인분만** 번역한다.

| 위키번호(참고) | 마커 | 프레임 | 매칭된 텍스트 | 매칭방식 |
|---|---|---|---|---|
| 9 | XLT | (New) Unifi mini Home | 누적 시술 +10,000건 … 포텐자 | 포함 |
| 10 | XLT | (New) Unifi mini Home | 포텐자 매끈한 피부결과 윤곽 | 포함(겹침→최소) |

**엣지 케이스:**
- `XLT` 코멘트가 `(x)` 프레임에 있으면 경고 후 사용자 의사 우선(단일 프레임 모드와 동일).
- 여러 `XLT` 코멘트가 같은 텍스트를 가리키면 dedup.
- 비텍스트 요소를 의도한 코멘트(좌표가 버튼·아이콘 위)는 확인 단계에서 사람이 거른다.
- **⛔ 팝업/모달 겹침 시 육안 검증(필수)**: 당첨/알림 **팝업·모달이 홈 등 배경 화면 위에 겹쳐 있는 프레임**은, 코멘트 핀 좌표가 **팝업 뒤 배경 텍스트**에 떨어져 오매칭될 수 있다(좌표 매칭은 z-order를 인식 못 함 — "포함 중 최소 bbox"가 배경의 작은 텍스트를 잡음). 예: 당첨 팝업의 `100JPYC 당첨됐어요!` 위 코멘트가 배경 `무신사 바우처`로 매칭된 실측 오류(2026-07 `mini_luckyball_voucher_musinsa`). **이런 겹침 화면은 어노테이션 이미지를 렌더해 핀이 팝업의 의도한 문구 위에 있는지 육안 확인**하고, 어긋나면 좌표 매칭을 무시하고 팝업 실제 문구로 수동 교정한다. 확인 단계 표의 `매칭방식`에 `팝업겹침→육안확인` 표기.

**산출물 연결**: 선별 결과(XLT Key + 번역)는 단일 프레임 모드와 동일하게 위키 `md/wiki.md` Mode B의 XLT 컬럼·다국어 번역 섹션 입력으로 넘긴다. **추가로, XLT 코멘트도 다른 코멘트와 동일하게 y좌표 순 번호(`1.`, `2.`…)를 부여하고, 위키 업데이트 시 Description 영역에 그 번호 + 코멘트 내용으로 함께 갱신한다** — XLT만 번역한 경우에도 XLT 컬럼·다국어 섹션만 채우고 Description을 빠뜨리지 않는다 (`md/wiki.md` Step 3 'Description 컬럼' 규칙).

### Step 2: XLT Key 생성
네이밍 규칙:
- 프리픽스: **담당 FE 팀에 따라 결정** (CLAUDE.md '⛔ 담당 FE 팀 규칙' 준수) — **UIT 팀 = `UF_` 고정**, **LV 팀 = 프로젝트 약어**(예: `KW_` = Kaia Wallet, `mini_guidekim_`). 위키에 UIT/LV 구분이 있으면 해당 영역 팀 규칙을 따르고, 없으면 팀을 물어 규칙 설명·적용 확인 후 진행
- 화면/기능 구분: `KW_home_`, `KW_terms_`, `KW_agg_`
- 의미 있는 suffix: `_title`, `_desc`, `_btn`, `_label`
- 예시: `KW_home_deposit`, `KW_terms_agree_all`
- **공통 문구**: 여러 화면에 공통으로 쓰이는 범용 문구는 `common_` 프리픽스 제안 + 위키 기존 키 재사용 (아래 '공통 문구 키 재사용 규칙' 참조)

**⚠️ 불변 규칙 (위반 시 프로토타입 i18n이 깨진다):**
1. **동일한 한국어 원문 = 반드시 1개의 키.** 같은 텍스트가 여러 화면·여러 맥락에 등장해도 키를 나누지 않는다 — 프로토타입 `I18N`은 한국어 텍스트를 키로 조회하므로 1:N 매핑이 불가능하다 (예: "전송하기"가 목록 버튼과 팝업 버튼에 모두 쓰여도 `KW_transfer_send_btn` 하나)
2. **번역 제외 판별 기준**: 한글이 없는 텍스트 중 숫자·금액·시간·지갑 주소·이메일·토큰 심볼(KLAY, USDT 등)·더미 데이터는 키를 부여하지 않는다. 단, **영문 UI 라벨**(예: `Imported wallet`, `Mnemonic wallet`)은 번역 대상일 수 있으므로 **사용자에게 포함 여부를 확인**한다
3. 브랜드명(Unifi 등) 단독 텍스트는 키를 부여하되 전 언어 동일 값으로 둔다 (guide.md 브랜드명 규칙)

**🔁 공통 문구 키 재사용 규칙 (반복·범용 문구는 키를 공유 — 불변 규칙 1의 확장):**

같은 한국어 문구는 화면이 달라도 하나의 키로 묶는다. 불변 규칙 1이 **한 run 안**의 중복을 막는다면, 이 규칙은 **위키에 이미 정의된 키**와 **여러 화면에 공통으로 쓰이는 범용 문구**까지 키를 공유해 번역·키 파편화를 막는다. 키는 아래 순서로 결정한다.

1. **위키 기존 키 우선 재사용 (신규 키 생성 금지)** — 번역 대상 한국어 문구가 **대상 위키 페이지의 「다국어 번역(XLT Full Translation)」 표에 같은 문구(ko_KR)로 이미 정의·번역된 키가 있으면 그 키를 그대로 사용**한다. 위키 storage의 다국어 표에서 ko_KR 셀이 동일한 행의 XLT Key를 찾아 매핑하고 새 키를 만들지 않는다 (위키 Mode B·단일 프레임·코멘트 선별 모드처럼 대상 위키가 정해진 경우 특히 필수 — 매 실행 위키 원문을 새로 조회해 대조한다).
2. **공통 문구는 `common_` 프리픽스 제안** — "회원가입", "로그인", "확인", "취소", "다음" 등 **여러 화면·기능에 공통으로 쓰이는 범용 문구**는 화면별 프리픽스(`mini_guidekim_`, `KW_home_` 등) 대신 **`common_` 프리픽스**(예: `common_signup`, `common_login`)를 쓰도록 **사용자에게 제안**하고, 승인받아 정의한다. 한번 `common_` 키로 정의된 문구가 다시 등장하면 1번에 따라 그 키를 재사용한다.
3. **확인 단계에서 함께 보고** — 재사용한 기존 키, `common_` 프리픽스 제안 대상, 신규 정의 키를 번역 확인(Step 5) 전에 사용자에게 함께 제시해 승인받는다.

### Step 4: 번역 수행

**⚠️ 5개 언어 모두 완전 번역 필수 — 일부 언어만 번역 금지**

**guide.md 규칙 준수:**
1. **한국어 원문 교정 (게이트 — 번역 전 필수)** — 맞춤법·띄어쓰기·표기 일관성을 먼저 정리(`md/check.md` 1단계). 교정으로 원문과 달라지면 `{Figma 원문 → XLT Key}` alias를 기록한다. 이 교정 없이 다국어 번역으로 넘어가지 않는다. **교정 수행 여부·alias는 게이트 리포트에 반드시 남긴다** — `scripts/check_gate_report.py`가 '한국어 원문 교정(1a)' 항목으로 확인하며, 누락 시 리포트가 미완결로 차단된다(교정 없거나 문서화 안 하면 완료 아님)
2. 용어집 매칭 — 동일 용어는 용어집 번역 사용
3. **5개 언어 번역 생성 (모두 필수):**
   - ✅ ko_KR: 원문 (오타 수정)
   - ✅ ja_JP: 정중한 です・ます体
   - ✅ en_US: 간결하고 명확
   - ✅ th_TH: 정중한 표현
   - ✅ zh_TW: 정식 번체
4. 치환자·변수 보존 — 표기는 **담당 FE 팀 규칙에 따른다: UIT 팀 = `{{0}}`(이중 중괄호), LV 팀 = `{0}`(단일 중괄호)** (다중 변수는 순서대로 UIT `{{0}}`,`{{1}}`… / LV `{0}`,`{1}`…), HTML 태그 `<span />` 보존. 팀 판별·확인은 CLAUDE.md '⛔ 담당 FE 팀 규칙' 참조
5. 번역 예외 항목 (USDT, IDRP 등) 원어 유지

**변수(치환자) 후보 탐지·제안 (가변 값):**
- 한국어 원문에서 런타임에 바뀔 수 있는 값(요율 `10%`, 건수 `1건`, 금액 `100만엔`, 기간 `7일` 등)을 탐지해 변수화를 **제안**한다 — 자동 적용 **절대 금지**, **변수화는 항상 사용자(PM) 확인을 받은 뒤에만 적용한다 (예외 없음)**.
- **치환자 표기는 담당 FE 팀 규칙을 따른다 — UIT 팀 `{{0}}`(이중), LV 팀 `{0}`(단일). 작업 시작 시 팀을 판별(위키 UIT/LV 구분) 또는 사용자에게 물어 확인한 뒤 맞춘다** (CLAUDE.md '⛔ 담당 FE 팀 규칙').
- 한 문장에 변수가 둘 이상이면 등장 순서대로 `{0}`, `{1}`… 부여. 5개 언어에 동일 인덱스로 넣고 위치만 어순에 맞게 조정.
- 수량 변수는 언어별 단/복수(plural) 분기가 필요할 수 있다 → XLT `plurals` 시트와 연동.
- "누적 +10,000건"처럼 마케팅 고정값일 수 있는 값은 단정하지 말고 제안만 한다. 확정 시 `{원문 → 변수형}` 매핑을 산출물에 보존.

**⚠️ 원문 교정·통합 시 alias 매핑 유지:**
- ko_KR 맞춤법 교정(예: `트랜젝션`→`트랜잭션`)이나 화면 간 표현 불일치 통합(near-duplicate 쌍을 1개 키로)을 했다면, **`{Figma 원문 → XLT Key}` alias 목록을 산출물에 함께 보존**한다
- 프로토타입 단계의 textNodes·i18n은 **교정 전 Figma 원문 텍스트**를 키로 매핑하므로, alias가 없으면 해당 텍스트의 XLT Key/번역 매핑이 누락된다
- 교정·통합 내역은 검증 리포트에 정리해 디자이너에게 원본 수정을 요청한다

**번역 진행 상황 보고:**
```
번역 중: {current}/{total} 텍스트 ({percent}%)
- ko_KR: ✓ 완료
- ja_JP: ✓ 완료
- en_US: ✓ 완료
- th_TH: ✓ 완료
- zh_TW: ✓ 완료
```

**절대 금지:**
- ❌ "ko_KR, en_US만 먼저 진행" 금지
- ❌ "나머지 언어는 나중에" 금지
- ❌ "일부 텍스트만 번역" 금지

### Step 5: 검증 및 품질 체크

> 🚧 **이 단계는 CLAUDE.md '⛔ 번역 품질 게이트'다 — 건너뛰면 작업 미완료.** 번역을 출력/위키/엑셀로 내보내기 전 반드시: ① `scripts/validate_translation.py` 실행, ② check.md 3단계 수행, ③ **P0/P1/P2 검증 리포트를 사용자에게 제시**(대화에 리포트가 없으면 완료 아님), ④ P0 0건 확인. **위키 통합 작업·코멘트 선별 모드에서도 동일.**

**⚠️ 필수 참조: `md/check.md`의 3단계 검증 프로세스를 따라야 합니다.**

#### 5.1 초기 검증
- [ ] 용어집과 일치하는지 확인
- [ ] 치환자/태그 보존 확인
- [ ] 동일 문서 내 같은 용어 같은 번역 확인

- [ ] 번역 예외 항목이 원어 유지되는지 확인

#### 5.2 심화 검증 (md/check.md 기반)
**번역 데이터를 임시 엑셀로 저장 후 3단계 검증 수행:**

임시 엑셀은 `translation_data.json`의 rows를 Step 7과 동일 규격(properties/plurals 시트, 첫 컬럼명 공백)으로 변환해 프로젝트 루트에 `xlt_validation_temp.xlsx`로 생성하고, `TranslationValidator(엑셀경로, 'scripts/glossary.json')`로 검증한다. **검증 통과 후 임시 엑셀은 삭제**한다 (최종 엑셀은 Step 7에서 별도 생성).

**1단계: 한국어 맞춤법·띄어쓰기 검토**
- [ ] 오타 확인 (`미선` → `미션` 등)
- [ ] 맞춤법 (`되요` → `돼요`, `됬-` → `됐-`)
- [ ] 띄어쓰기 의존명사 (`유지시` → `유지 시`, `할수있-` → `할 수 있-`)
- [ ] 비표준 공백 (`\xa0` 등) 제거
- [ ] `/n` 오타 → `\n` 수정
- [ ] 표현 어색함 확인 (`미션하고` → `미션 완료하고`)
- [ ] 조사 누락 확인
- [ ] 종결 어미 일관성 (해요체 vs 합쇼체)

**2단계: 용어집 위반 확인**
- [ ] 한국어 키워드 매칭 (용어집 API 조회 결과 기준)
- [ ] 예외 패턴 표기 통일 (USDT, JPYC, PIN, API, URL, Apple, Google, IDRP)
- [ ] zh_TW 한자 변형 통일 (`產` U+7522 표준 번체)
- [ ] th_TH 자산 표기 일관성 (`สินทรัพย์`)
- [ ] 도메인 핵심 용어 일관성

**3단계: 다른 언어 번역 검토**
- [ ] 빈칸 확인 (모든 언어 셀 채워졌는지)
- [ ] 언어 혼입 (en_US 셀에 한글 등)
- [ ] placeholder 일치 (`{0}`, `{1}` 등)
- [ ] `/n` 오타 확인
- [ ] 컬럼 swap 탐지 (en_US ↔ ko_KR 등)
- [ ] ja_JP 한국어 직역 패턴 (`出席` → `チェックイン`)
- [ ] 한 문장 내 단어 중복
- [ ] 마침표 일관성 (언어별 관습 준수)

### Step 7: 엑셀 파일 생성
번역 데이터를 XLT System 업로드용 엑셀 파일로 변환합니다.

**파일 저장 위치:**
```
프로젝트루트/xlt/xlt_output_{날짜시간}.xlsx
예: xlt/xlt_output_20260610223056.xlsx
```
- xlt 폴더가 없으면 자동 생성
- 파일명 형식: `xlt_output_YYYYMMDDHHmmss.xlsx`
- **위키 연동**: 위키 업데이트와 함께 진행할 때는 이 엑셀을 Confluence 페이지에 **첨부**하고 다국어 번역 섹션에 다운로드 링크를 넣는다 (`md/wiki.md` 'XLT 엑셀 첨부' 규칙)
- 프로젝트 폴더 내에서 XLT 파일을 통합 관리

**엑셀 구조:**

#### Sheet 1: properties
| 컬럼 | 설명 | 예시 |
|------|------|------|
| Unnamed: 0 | XLT Key (컬럼명은 공백) | `KW_home_deposit` |
| en_US | 영어 번역 | `Deposit` |
| ko_KR | 한국어 번역 | `입금하기` |
| ja_JP | 일본어 번역 | `入金する` |
| zh_TW | 중국어 번역 (번체) | `存入` |
| th_TH | 태국어 번역 | `ฝาก` |

**중요:**
- 첫 번째 컬럼은 헤더가 없어야 합니다 (`Unnamed: 0`으로 pandas가 인식)
- 줄바꿈이 포함된 텍스트는 셀 내에 그대로 유지 (`\n` 문자 보존)
- 모든 셀은 텍스트로 저장 (빈 값 없음)

#### Sheet 2: plurals
복수형 처리 규칙 (고정값):

| Unnamed: 0 | en_US | Unnamed: 2 | ko_KR | ja_JP | zh_TW | th_TH |
|------------|-------|------------|-------|-------|-------|-------|
| (빈 값) | one | other | other | other | other | other |

**생성 방법:**
Python pandas 사용 (openpyxl 엔진):
```python
import pandas as pd
from datetime import datetime
import os

# xlt 폴더 생성
xlt_dir = 'xlt'
os.makedirs(xlt_dir, exist_ok=True)

# 번역 데이터를 DataFrame으로 변환
df_props = pd.DataFrame(translation_data)

# plurals 시트 데이터
df_plurals = pd.DataFrame([{
    'Unnamed: 0': None,
    'en_US': 'one',
    'Unnamed: 2': 'other',
    'ko_KR': 'other',
    'ja_JP': 'other',
    'zh_TW': 'other',
    'th_TH': 'other'
}])

# 엑셀 파일 생성
filename = f"{xlt_dir}/xlt_output_{datetime.now().strftime('%Y%m%d%H%M%S')}.xlsx"
with pd.ExcelWriter(filename, engine='openpyxl') as writer:
    df_props.to_excel(writer, sheet_name='properties', index=False)
    df_plurals.to_excel(writer, sheet_name='plurals', index=False)

print(f"✓ XLT 엑셀 파일 생성: {filename}")
```

- [ ] xlt 폴더가 생성되었는지 확인
- [ ] properties 시트에 모든 XLT Key와 번역이 포함되었는지 확인
- [ ] 첫 번째 컬럼명이 비어 있는지 확인 (Unnamed: 0)
- [ ] 줄바꿈 문자가 보존되었는지 확인
- [ ] plurals 시트가 고정 포맷대로 생성되었는지 확인
- [ ] Excel에서 파일을 열어 데이터 무결성 확인

## 키 단위 번역 패치 모드 (XLT Key Translation Patch)

> **이미 위키·엑셀에 반영된 번역에서, 특정 XLT Key의 일부 언어만 바꿔야 할 때** 쓰는 모드. 프레임 전체 재처리 없이 키·언어 단위로 외과적 갱신한다. 문구가 여러 부서 검토를 거쳐 ⓐ 한국어가 바뀌어 전체(또는 일부) 언어가 바뀌거나 ⓑ 특정 언어만 최종본으로 교체되는 상황을 처리한다.

### 트리거 / 입력 포맷 (사용자 제공)
대상 위키 URL + 아래 형식:
```
[번역 패치]  대상 위키: https://...
- 키: mini_guidekim_xxx
  · ko_KR = "새 한국어"            # (A) 한국어 변경 → 전 언어 재번역, 유지할 언어는 keep 지정
    keep: zh_TW                     #   (선택) 재번역에서 제외해 보존할 언어
  또는
  · th_TH = "...", ja_JP = "..."   # (B) 부서 제공 최종본 → 지정 언어만 그대로 교체(나머지 보존)
- (키 여러 개 가능)
```

### 서브모드
| 모드 | 트리거 | 값 산출 방식 | 게이트 역할 |
|---|---|---|---|
| **(A) ko-source** | `ko_KR` 변경 | ko 교정 후 **update 대상 언어 재번역**(LLM, guide/용어집 적용), keep 언어 보존 | 번역 검증(변경 키) |
| **(B) lang-specific** | 특정 언어만 제공 | **제공 최종본 그대로 사용**(임의 개선 금지) | 제공 카피 **무결성 검증**(빈칸·placeholder·태그·용어집·언어혼입) |

### 절차
1. **토큰 확인** + 대상 위키 URL 확정.
2. **라이브 조회(캐시 금지)**: 위키 storage(다국어 표 + Screen XLT) + 현재 첨부 엑셀(또는 다국어 표 파싱)으로 **현행 번역** 확보. 대상 키 존재 확인(없으면 신규 추가 흐름인지 사용자 확인).
2-1. **⛔ 컬럼 정렬 검증 (단일/일부 언어 패치 전 필수 — 예외 없음)**: 특정 언어만 바꿀 때(예: "일본어만 업데이트"), **바꿀 언어 diff만 보고 패치하지 않는다.** 패치 대상 키마다 **엑셀의 5개 언어 셀을 전부 위키 다국어 표(정본)와 대조**해, 각 언어 컬럼이 실제로 그 언어 내용을 담고 있는지 확인한다. **컬럼 misalignment(한 언어 칸에 다른 언어 내용, 예: `ja` 칸에 한국어·`en` 칸에 일본어)가 있으면 단일 언어 패치로 진행 금지** — 그대로 덮어쓰면 그 칸에 있던 **다른 언어의 유일한 원본이 소실**된다(2026-07 `mini_guidekim_cat_eye`류 회전 어긋남 실측: `ja`만 덮어써 한국어 소실). 이 경우 **그 키의 어긋난 컬럼 전부를 위키 정본으로 realign**해 패치 스펙에 포함하고, 변경 사실(어긋난 컬럼·before→after)을 리포트·History에 명시한다. 위키 표가 정렬 정본이다. ([[xlt-single-lang-patch-verify-columns]])
3. **값 확정**: (A)면 ko 교정→update 언어 재번역(keep 제외), (B)면 제공값 그대로. → 키별 `{lang: 최종값}` 패치 스펙 구성. **2-1에서 misalignment가 발견된 키는 어긋난 언어 셀도 정본값으로 함께 스펙에 넣는다.**
4. **⛔ 품질 게이트(변경분, 필수)**: 패치 적용본으로 `scripts/validate_translation.py` 실행 + `md/check.md` 수동(변경 키·변경 언어) → **P0/P1/P2 + 처리 판정 + (d) 추가 개선·제안** 리포트 제시. P0=0 확인. (A)는 ko 원문이 Figma와 달라지면 **alias 기록 + 디자이너 원본 수정 요청**.
5. **결정론적 적용**: `scripts/patch_translation.py`의 `apply_translation_patch(rows, patches)`로 **지정 언어 셀만 교체, 나머지 보존**(무결성 가드: 키 존재·언어명·빈 값). → `export_to_xlt.create_xlt_excel`로 엑셀 재생성. **⛔ 컬럼 정렬 가드(1g) 내장**: 패치 적용 후에도 대상 키 행의 언어 칸에 이질 문자체계(ja칸 한글·en칸 한자 등)가 남으면 `ValueError`로 **차단**한다 — 단일 언어만 바꾸지 말고 어긋난 컬럼 전부를 정본으로 realign(Step 2-1)해야 통과한다. 의도적 예외만 `allow_misaligned=True`.
6. **위키 반영(외과적)**: 다국어 표 해당 키 행의 **변경 언어 셀만 교체** + (A에서 ko 변경 시) Screen XLT 중첩표의 KR·해당 Description 문구 갱신 + view-file 매크로 파일명 갱신 + History 행 추가. **라이브 rebase 후 PUT**(동시편집 대비, [[wiki-concurrent-edit-hazard]]).
7. **엑셀 재첨부** + **검증**: 라이브 재조회로 셀 반영·버전 증가 확인.

### 엣지/주의
- **컬럼 정렬 먼저(2-1) — 단일 언어 diff 맹신 금지.** "일본어만"처럼 한 언어만 바꿔도 대상 키의 5개 언어를 위키 정본과 대조한다. `ja` 칸에 한국어가, `en` 칸에 일본어가 들어간 회전 어긋남 키를 diff 없이 덮어쓰면 다른 언어 원본이 소실된다. misalignment 키는 어긋난 컬럼 전부를 정본으로 realign.
- `keep`과 `update` 충돌, ko 변경인데 update 언어 미지정(기본=keep 제외 전 언어 재번역) → 사용자 확인.
- (B) 부서 제공 최종본은 **번역하지 않고 그대로** 넣되, placeholder(`{0}`)·태그·용어집 표기는 검증한다.
- ko만 바뀌고 미지정 언어는 보존이 기본 — 전체 재번역로 인한 의도치 않은 변경을 막는다.
- 변경은 **다국어 표 + Screen XLT(KR) 양쪽**에 정합되게 반영(ko 변경 시).
