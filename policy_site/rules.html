1. 목적과 범위

  • 목적: 기획팀이 관리하는 현재 확정 정책을 타 팀(사업·운영·CS·개발)과 기획팀이 빨리 찾게 한다. 이 사이트는 요약본이고 정본은 항상 위키다.
  • 대상 서비스: Unifi(웹) · Unifi mini만. Unifi Pay · Kaia · Unifi Mobile · Kaia Wallet App은 넣지 않는다.
  • 대상 기간: 2026-09 이후 배포(Unifi v1.7.x~ · Unifi mini v2.0.0~)와 그 이후 예정 배포.
  • 넣지 않는 문서: 개발 설계 문서 · 스크럼 · 회의록 · 번역 검수 페이지 · 개인 초안. 이런 문서는 근거로도 쓰지 않는다.

3. 근거 규칙 — 추측 금지

⛔ 정책 내용은 위키 원문만 근거로 쓴다. 기억·Slack 요약·다른 사이트의 설명으로 채우지 않는다. 위키에서 확인이 안 되면 그 항목은 「확인 필요」로 둔다.
  1. 원문은 매번 새로 조회한다. 이전에 저장한 사본을 쓰지 않는다. 판수(version.number)를 조회 결과에서 그대로 적는다.
  2. 수치·기간·비율·조건은 원문 표기 그대로 쓴다(예: 「결제일 + 90일」, 「80%」). 반올림·환산·의역하지 않는다.
  3. 취소선(<s>·<del>) 구간은 폐기된 내용이다. 현재 정책으로 쓰지 않는다.
  4. 한 문서 안에 날짜가 붙은 결정이 여러 개면 날짜가 가장 늦은 결정을 따른다.
  5. 여러 문서가 같은 정책을 다루면, 그 정책을 직접 정의한 정책 정본 문서 > 화면 정의 문서 > 상위 기획서 요약 순으로 따른다. 순서가 분명하지 않으면 「확인 필요」로 두고 양쪽 근거를 모두 적는다.
  6. 🔴·「미정」·「TBD」·「확인 필요」가 붙은 내용은 확정으로 쓰지 않는다.
  7. 문구 전체를 옮겨 적지 않는다 — 요약 1~3문장 + 원문 위치(절 이름)만 쓴다.

4. 상태 판정

상태뜻판정 기준
최신현재 배포에 적용된 확정 정책정본에서 확정 · 열린 쟁점 없음

예정아직 배포 전배포 이력에서 그 과업의 버전이 「배포 완료」가 아님
폐기더는 적용 안 됨위키에서 폐지 결정·취소선. 독자가 예전 정책을 물을 때를 위해 남긴다

5. 적용 버전 — 배포 이력 기준

  • 출처: Now Platform Unifi 프로덕션 배포 현황 https://now.linenextcorp.com/unifi/production.html#deploy (SSO 로그인 필요 — 로그인은 사용자가 한다).
  • 로그인된 브라우저에서 페이지가 쓰는 /unifi/api/jira/production/deploy JSON을 읽고, product == "Unifi"인 버전만 쓴다(Unifi mini 포함).
  • 정책의 release는 그 정책을 담은 과업이 들어간 버전이다. 과업의 「기획서」 링크가 정본 위키와 같으면 그 버전을 고른다. 못 찾으면 비워 둔다(추측 금지).
  • releases 목록에는 정책과 관련된 Feature 과업만 남긴다. 내부 개선·QA 핫픽스는 정책을 바꾸는 것만 남긴다.

6. 데이터 형식 — data.js

사이트의 내용은 data.js 한 파일뿐이다. HTML·CSS·JS는 고치지 않는다(바꿀 일이 있으면 사용자 확인).

window.POLICY_DATA = {

  • 기존 카드를 고칠 때는 그 카드만 고친다. 다른 사람이 만든 카드를 정리·재작성하지 않는다.
  • 같은 정책이 이미 있으면 새 카드를 만들지 않고 기존 카드를 갱신한다(제목·키워드로 먼저 검색).
  • 판수가 오른 위키를 다시 읽었으면 내용이 같아도 source.version·checkedAt을 갱신한다.

7. 작업 절차 (Claude)

  1. 최신 소스 확보 — 정본 소스는 GitHub planning_system_with_figma 저장소의 policy_site/다. 저장소가 있으면 git pull 후 작업한다. 없으면 DropWeb MCP read_site_files로 라이브 data.js를 받아 그 위에 고친다(다른 사람의 최신 변경을 덮지 않기 위해 — 작업 시작 시점과 게시 직전에 두 번 확인).
  2. 정본 위키 조회 — Confluence MCP 또는 REST로 대상 페이지 원문과 판수를 새로 읽는다. 하위 페이지·관련 결정 문서도 확인한다.
  3. 배포 이력 조회 — 5절. 로그인이 안 돼 있으면 사용자에게 로그인을 요청한다.
  4. 카드 작성 — 3·4·6절. 추측이 필요한 칸은 비우거나 「확인 필요」.
  5. 검사 — 저장소가 있으면 python3 scripts/check_policy_site.py --live 실행 → exit 0. 저장소가 없으면 6절 형식을 직접 대조하고 node -e로 data.js가 문법 오류 없이 읽히는지 확인한다.
  6. 사용자 확인 — 추가·변경·삭제 카드를 표(제목 · 이전 → 이후 · 근거 위키 판수)로 보여 주고 승인을 받는다.
  7. 게시 — ⛔ 사용자 승인 후에만. 사이트 폴더를 ZIP으로 묶고(cd policy_site && zip -qr ../dropweb/unifi_policy_vN.zip . -x ".*" "service-spec.md"), DropWeb MCP update_site(site_id · change_summary 필수 · file_path=ZIP 절대경로)를 호출해 돌려받은 업로드 명령을 로컬에서 실행한다. HTTP 409가 나오면 다른 사람이 먼저 재배포한 것이다 — 덮어쓰지 말고 라이브 data.js를 받아 합친 뒤 다시 만든다. 게시 후 MCP get_site로 수정일·원본 파일명을 확인한다.
  8. 기록 — service-spec.md 변경 이력에 한 줄 추가하고 저장소에 커밋한다.

8. 금지

  • ⛔ 이 작업 중에 위키를 고치지 않는다(읽기만). 위키가 틀려 보이면 사용자에게 알린다.
  • ⛔ 토큰·비밀번호·API 키를 파일·커밋·메시지에 남기지 않는다.
  • ⛔ 새 DropWeb 사이트를 만들지 않는다 — 항상 기존 Unifi Policy 사이트에 재배포한다.
  • ⛔ 개인정보(유저 ID·이메일·주문번호)와 미공개 사업 수치(매출·정산)를 넣지 않는다.
  • Pay·Kaia·Mobile 정책, 개발 설계 문서 내용을 넣지 않는다.

9. 리뷰 페이지 — 충돌 · 미결 모으기

review.html은 카드의 review 항목을 모아 기획팀이 결정할 것을 보여 준다. 카드를 만들거나 고칠 때 아래 중 하나에 해당하면 review를 단다.

kind언제카드 상태
상충근거 문서끼리 내용이 다르다확인 필요
미정🔴 · TBD · 「확정 필요」로 아직 정해지지 않았다확인 필요
정본 없음근거가 될 정책 문서가 없거나 열리지 않는다확인 필요
문서 불일치결정은 났지만 다른 문서에 낡은 서술이 남아 있다최신 · 변경됨 유지
세부 미결카드 내용은 확정인데 세부 사항 하나가 남아 있다최신 · 변경됨 유지
  • question은 기획팀이 결정할 것 한 문장으로 쓴다(「~인가?」 · 「~을 정한다」). 근거는 source·conflicts에 적은 것이 그대로 보인다.
  • ⛔ 상태가 「확인 필요」인 카드는 반드시 review가 있어야 한다(검사 스크립트가 막는다).
  • 리뷰 페이지에서 결정하지 않는다 — 결정은 정본 위키에 기록하고, Claude가 위키를 다시 읽어 카드를 고친 뒤 review를 지운다. 이 페이지에 결정 내용을 적어 정본처럼 쓰지 않는다.

10. 완료 체크리스트

  • ☐ 모든 카드의 정본 위키를 이번 작업에서 새로 조회했다(판수 기록)
  • ☐ 수치가 원문과 글자 단위로 같다
  • ☐ 확인 필요 카드에 양쪽 근거가 있다 · 변경됨 카드에 변경 이력이 있다
  • ☐ check_policy_site.py --live exit 0 (또는 형식 수동 대조)
  • ☐ 사용자 승인 후 게시 · get_site로 확인
  • ☐ service-spec.md 변경 이력 · 커밋
