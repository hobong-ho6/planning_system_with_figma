## 3. 실패 3건과 원인

### 실패 ① 감시 범위를 스레드 1개로 잡았다 (치명)
- **증상**: 정확히 감시 목적이었던 멘션을 놓쳤다. 사용자가 직접 발견했다.
- **원인**: 사용자의 첫 요청이 "이 스레드"였고 나는 그 문자 그대로 걸었다. 그러나 **사람이 원한 건 "나를 부르는 일"이지 "그 스레드"가 아니다.** 멘션은 스레드를 가리지 않는다.
- **교훈**: 감시 단위는 **스레드가 아니라 사람(멘션 대상)**이다. 범위를 좁히면 "감시 중"이라는 안전감만 주고 정작 놓친다 — 감시하지 않는 것보다 나쁠 수 있다.

### 실패 ② 초안 말투가 본인과 달라 그대로 못 썼다
- **증상**: 3문단짜리 정중한 영문 초안 → 사용자가 직접 7단어로 답글(`you can use this mini_voucher_detail_max_benefit_badge`).
- **원인**: 초안을 쓰기 전에 **본인 과거 발화를 한 번도 보지 않았다.** 일반적인 비즈니스 영어 기본값으로 썼다.
- **교훈**: 남의 이름으로 쓰는 글은 **말투 실측이 선행 조건**이다. 붙여넣을 수 없는 초안은 가치가 0이다(오히려 읽는 시간만 쓴다).
- **부수 발견**: 이 사람은 **같은 답을 상대가 달라도 글자 그대로 재사용**한다. "상대가 맥락을 모르니 설명을 붙이자"는 내 판단이 틀렸다.

### 실패 ③ 기준선(baseline)이 cron 프롬프트에 하드코딩됐다
- **증상**: 프롬프트 텍스트가 고정이라 매 실행이 같은 기준선을 쓴다 → 이미 처리한 건을 계속 새 멘션으로 재보고할 위험.
- **임시 대응**: 처리할 때마다 `CronDelete` + `CronCreate`로 기준선을 올린 프롬프트를 재등록(3회 수행).
- **교훈**: **폴링 루프에는 쓰기 가능한 상태 저장소가 필요하다.** 프롬프트는 상태를 담는 그릇이 아니다.

## 4. 잘 작동한 것

- **멘션 → 영향도 사전 조사 파이프라인**: 멘션을 찾은 뒤 레지스트리 3키를 실조회하고 위키와 대조해 "원복하면 `_rate`와 `_badge`가 완전 중복된다"는 판단 재료를 사람이 답하기 전에 준비했다. 이게 이 시스템의 본체 가치다.
- **등록 결과 역검증**: 사용자가 XLT 업로드를 마친 뒤 시스템에서 5개 언어를 재조회해 엑셀과 완전 일치를 확인했다(1,685 → 1,686키).
- **요청 충돌 감지**: catrius(제거)와 An Vo(유지)의 상충을 스레드 교차로 짚어냈다. 사람이 놓치기 쉬운 지점이다.
- **승인 경계**: 게시·등록·위키 수정을 한 번도 임의 실행하지 않았다. 스레드 내용을 지시가 아닌 데이터로 다뤘다.

## 6. 신규 프로젝트에서 만들 것 (제안)

1. **`scripts/watch_slack_mentions.py`** — 멘션 스캔을 스크립트로 고정한다. 인라인 재구현 금지(`fetch_comments.py`와 같은 이유).
   - 입력: 채널 목록 · 감시 대상 user id · 제외 user id(본인·봇)
   - 상태: `reports/slack-watch/state.json`에 채널별 마지막 확인 ts 기록 → **실패 ③ 해소**
   - 출력: 신규 멘션 목록(스레드·작성자·본문·첨부 유무)
2. **말투 규칙을 초안 생성의 선행 단계로 강제** — 대상자별 말투 파일(`memory/slack-reply-tone.md` 형식)이 없으면 **초안을 쓰지 않고 먼저 실측**한다.
3. **첨부 이미지 분기** — 첨부가 있는 멘션은 "이미지 확인 필요"로 분류해 사람에게 즉시 넘긴다. 추측으로 진행하지 않는다.
4. **영향도 조사 템플릿화** — XLT 키가 언급된 멘션이면 ⓐ 레지스트리 실조회 ⓑ 위키 대조 ⓒ 같은 문구 다른 키 검색을 자동 수행(이번에 수동으로 한 것).
5. **감시 범위 기본값을 "사람"으로** — 스레드·채널은 필터일 뿐 단위가 아니다. **실패 ①의 재발 방지책.**
